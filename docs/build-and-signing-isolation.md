# Build and signing-key isolation

This page says how the release pipeline of this repository keeps builds apart from each other and keeps the signing key away from every build. It describes what the v0.3 release chain does; each claim links to the workflow, job or script that does it. The wording is "designed to meet" and "maps to": this is not a certification, and nothing here says the project is compliant with, or certified against, any framework.

## 1. Every build is its own job

A GitHub-hosted job runs on its own virtual machine. GitHub documents it this way: "each job runs in a fresh instance of a runner image" ([workflow syntax, runs-on](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)), and "GitHub-hosted runners execute code within ephemeral and clean isolated virtual machines" ([secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)). Permissions and secrets are set per job: a secret kept in a deployment environment is "only available to workflow jobs that reference the environment" ([deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)). The pipeline uses those facts, and only those, as its isolation unit.

| Stage | Job | What runs there | Secrets and tokens it holds |
|---|---|---|---|
| Build ([stage-build.yml](../.github/workflows/stage-build.yml)) | `apk`, one job per architecture | the apk build | no stored secret, no identity token; a read-only job token for admission |
| Build | `assemble` | the image assembly | no stored secret, no identity token |
| Rebuild ([stage-reproducibility.yml](../.github/workflows/stage-reproducibility.yml)) | `rapk`, `rapk-arm`, `assemble` | the same two steps, rebuilt from the same commit (the apk on each architecture, then the image assembly) | no stored secret, no identity token |
| Sign ([stage-sign.yml](../.github/workflows/stage-sign.yml)) | `sign`, `sign-rebuild`, `sign-check` | the signatures on the records of Build, Rebuild and Check (`sign` also signs the provenance) | an identity token in each job, used only to reach the release key in AWS KMS; builds nothing |
| Check ([stage-verify.yml](../.github/workflows/stage-verify.yml)) | `check-govulncheck`, `check` | building the govulncheck scanner; scanners, acceptance and runtime checks on Build's images, the dist archives and the guide, on both chips (one matrix job) | no secret, no identity token; builds no apk or image |
| Release ([stage-promote.yml](../.github/workflows/stage-promote.yml)) | `compare` | the comparison of Build's and Rebuild's apks (their control and data sections; the signature of each is checked against the committed key) | contents read only: no secret, no environment, no identity token |
| Release | `verify` | verification of every earlier stage's record | contents read only: no secret, no identity token |
| Release | `release` | signing and publishing | the job may request an identity token (`id-token: write`); the Witness steps get the role and key reference for the release key in AWS KMS; the job's GitHub token, in the checkout and in the publish, sign and assets steps (ghcr.io and release assets); the Docker Hub secrets, in the publish and sign steps only; write permissions (environment `release`) |

No build job holds a stored secret. Builds do not share a machine with the job that signs or publishes.

## 2. How artifacts cross jobs

Jobs pass files as workflow artifacts. Build writes a digest list and a Witness record of what it did; Sign signs the records after checking them: `sign` Build's, `sign-rebuild` Rebuild's, `sign-check` Check's. The jobs that run or decide something on a previous stage's output start by checking that stage's record against the digest list: Rebuild checks Build's record and its own apk records, Check and Sign check Build's, and the Release stage's `verify` job checks every earlier stage's record; the `release` job repeats that check on its own downloads before any other step that signs or publishes ([release-verify.sh](../bin/release-verify.sh)). The Release stage's `compare` job has no secret and no identity token. It checks Rebuild's signed apk records and binds Rebuild's apks to them, then compares Build's and Rebuild's apks (checking each apk's signature against the committed key); its result file is accepted only after `verify` has authenticated the records and checked the result against the apk digests Build attested. Images are promoted by digest, never rebuilt ([stage-promote.yml](../.github/workflows/stage-promote.yml), [release-publish.sh](../bin/release-publish.sh)). Rebuild makes its own copy of the apks and images from the same commit in its own jobs ([stage-reproducibility.yml](../.github/workflows/stage-reproducibility.yml)) and compares every item, the apk digests included, with Build's before it signs its verdict.

## 3. The signing key and the signing identities

- **The release signing key** is held in AWS KMS and never leaves it. A job that signs asks KMS to sign with a short-lived identity token. Only the Sign stage's jobs ([stage-sign.yml](../.github/workflows/stage-sign.yml)) and the `release` job ([stage-promote.yml](../.github/workflows/stage-promote.yml)) are given the role for that key. Every step of the `release` job can request an identity token (`id-token: write` is set on the job); the job gives the role and key reference to each of its Witness steps (`release-verify`, `release-apks`, `release-publish`, `release-sign`, `release-assets`, `release-postverify`), because each one signs its own record with the key; `release-apks` and `release-sign` also sign release files with it ([release-apks.sh](../bin/release-apks.sh), [release-sign.sh](../bin/release-sign.sh)). The Docker Hub secrets reach only the `release-publish` and `release-sign` steps; the job's GitHub token reaches those two, `release-assets` and the checkout step.
- **The release job receives no apk or image that Rebuild made.** What it signs and publishes starts from Build's exact artifacts (Build's apks, re-signed with the release key, and Build's images, copied by digest) and adds the release evidence it creates; beside them it receives only the earlier stages' records (Build, Sign, Rebuild, Check), Check's results and the small comparison result. Each apk it signs must first have exactly the digest Build attested ([release-apks.sh](../bin/release-apks.sh)).
- **The Rebuild comparison runs in a job with no secrets and no identity token** (`compare`, [stage-promote.yml](../.github/workflows/stage-promote.yml), [release-compare.py](../bin/release-compare.py)). It checks Rebuild's signed apk records against Rebuild's apks. The only thing that leaves it is a small result file, which `verify` and `release` read; `verify` accepts it only as a pass for the apk digests Build attested ([chain-verify.py](../bin/chain-verify.py), command `apk-compare`).
- **Every signature a release ships uses the release key in AWS KMS.** There is no keyless signing and no short-lived certificate. Two earlier signatures are replaced before release: the throwaway-key signature Witness puts on each record when it is made (the final record carries the release-key signature, [witnessed.sh](../bin/witnessed.sh)), and the signature on an apk when Build makes it, which `compare` checks against the committed assembly key (`build/keys/assembly.rsa.pub`, [release-compare.py](../bin/release-compare.py)) and `release-apks` then re-signs with the release key. The Sign stage signs the records of Build, Rebuild and Check, and the provenance ([stage-sign.yml](../.github/workflows/stage-sign.yml)). The `release` job signs the apks, the images, the release policy and the other release files, and the record of each of its own steps ([release-apks.sh](../bin/release-apks.sh), [release-sign.sh](../bin/release-sign.sh), [witnessed.sh](../bin/witnessed.sh)). Each release-key signature has an entry in a public transparency log (Rekor). Jobs of the Build, Rebuild and Check workflows have no identity token, so they cannot ask KMS to sign.

## 5. Known gaps

- **No hardware separation per build.** GitHub-hosted jobs give VM-level separation. Per-build hardware separation (SC-39(1)) is not something hosted runners let us show, and we do not control the hardening of the runner image; both are listed here as one gap.
- **Provenance made inside a build job is not unforgeable by itself.** Witness records a build step with a throwaway key made for that step in a private directory and removed when it returns, but any step of the job could make a key of its own and write a record with it. That is why the stages check the previous stage's record against its inputs, and `verify` checks the apk comparison against Build's attested digests, before anything is accepted for signing or publishing (section 2).
- **The two image variants share a job.** `assemble` builds the production and the `-fips` image in the same job, in Build and in Rebuild, from the same verified inputs with the same script. We count that as one build; each build, in the sense of Build, Rebuild and each architecture, is its own job. Splitting the variants into separate jobs is possible and is an option after the first release candidate.
- **No automated rotation of the release signing key is claimed** (KSI-SVC-06 asks for "regular rotation").
- **The release pipeline's own signing tools are not claimed to be FIPS-validated** (SC-13).
